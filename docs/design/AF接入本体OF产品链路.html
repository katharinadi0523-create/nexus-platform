01 · 先核对前提

OF 文档里有三处和“只要有 Key 就行”对不上

依据是开发环境 API 目录（2026-11-14 快照，106 个接口），只读了页面文档，没有实际调用。下面三条决定了“用户填 Key”方案能不能做到完全不依赖 OF 改造。

  • Key 的范围可能是“一个场景”，不是“整个工作空间”冲突依据

    OF 调用流程第一步是“应用注册：注册调用方应用并绑定本体场景”，鉴权说明写“每个应用绑定一个本体场景，只能访问该场景内已授权能力”，Key 还能按能力包（查询 / 写入 / 链接 / 行为执行）开通。这和“一个 Key 能调用对应工作空间的所有场景”不一致。

    影响：如果 Key 只绑一个场景，“填 Key 后列出场景库让用户选”这一步会退化成“填 Key 后显示它绑定的那个场景”。流程反而更简单，但界面文案和校验逻辑不同，要先问清楚。

  • 只有 Key 不够，每个请求还要带 Workspace Id 等三个头冲突依据

    鉴权说明要求每个接口除了 Authorization: Bearer {API_KEY}，还要带 X-Ceai-User-Id、X-Ceai-Tenant-Id、X-Ceai-Workspace-Id，原文是“Workspace Id 不填时页面看不到数据”。列场景的接口 HttpListOntologyModel（API011）请求体里 workspace_id 也是必填。示例 curl 里还有 x-regionid。

    影响：使用端“不能自己带上 workspace id”的问题依然存在，只是换了个来源：不是 AF 带，而是用户从 OF 抄过来和 Key 一起填。这样仍然不需要 OF 改造，代价是表单多一个字段。User Id 填谁（Key 创建者？AF 当前用户？）文档没说，见待确认。

  • OF 自己提供了“本体 MCP 服务”和开放问答接口依据

    文档说“讲 MCP 协议的智能体优先走「本体 MCP 服务」”，与 API 共用同一套鉴权。另有 HttpStreamCopilotMessage / HttpGetCopilotConversationDetail（API105/106）：OF 侧的问答智能体，异步提问 + 轮询结果，带交互卡片。这两点直接影响第 08 节“子智能体怎么实现”。本次快照里没有 MCP 服务的工具清单。

02 · 核心主张

同意“两端都让用户自己填 Key”，再补三条规则

  • 一套绑定流程，两端共用。不管在管控端还是Claw，都是：填 OF 凭证（Key + Workspace Id）→ AF 调 OF 校验并列出可用场景 → 选一个场景 → 绑到智能体上。AF 不需要知道 OF 的工作空间结构，也不需要 OF 改造。
  • 凭证和绑定分开存。凭证叫“OF 连接”，是一份可复用资源：管控端归项目，Claw归个人。智能体只引用“连接 + 场景 ID”，不复制 Key。Key 过期或轮换时只改一处。
  • 发布出去用的是发布者的 Key。广场上任何人调用这个智能体，访问 OF 的身份和权限都是那把 Key 的，不是调用者自己的。发布时要明确提示，并建议 Key 只开查询能力包。
  • 个人 Key 不随发布带出。Claw 里个人绑定的 OF 连接只给本人用，和《预置付费插件怎么放》的规则保持一致。
  • OF 调用放进子智能体。主智能体只看到一个“问本体”的入口；子智能体里只装运行时需要的十来个接口，建模、仿真、连接器、自动化规则这些管理类接口一律不暴露。

04 · 对象模型

两个新对象：OF 连接、本体绑定

OF 连接 OntologyConnection ├ id, name # 如“供应链本体·生产” ├ ownerScope # project | personal ├ ownerId # 项目 ID 或用户 ID ├ apiKey # 加密存储，界面只显示后 4 位 ├ workspaceId # 用户从 OF 抄 ├ tenantId / userId # 待确认，见 01 ├ status # 可用 | 失效 | 未校验 ├ lastVerifiedAt └ createdBy
本体绑定 AgentOntologyBinding ├ agentId # 一个智能体最多一条 ├ connectionId ├ ontologyModelId # 即 OF 的场景 ID ├ sceneNameSnapshot # 绑定时的名称，场景删了也能提示 ├ capabilities # 查询 | 执行行为（默认只查询） └ catalogDigest # 语义目录摘要，供子智能体提示词

为什么连接要独立成资源：一个项目里多个智能体可能用同一个 OF 工作空间；Key 轮换、失效排查都只看一处。建议管控端把它放进项目“资源 / 凭证”一类，和预置付费插件的组织 Key 放在同一个地方。

“最多绑一个场景”落在 AgentOntologyBinding.agentId 唯一。多个场景的需求用“多个智能体各绑一个，再由上层智能体召唤”解决，不放开这个限制。

05 · 管控端流程

在智能体编辑页绑定本体

绑定步骤

  1. 智能体编辑页 → 能力配置 → “本体”区块，点“绑定本体”区块只允许一项，已绑定时按钮变成“更换”
  2. 选择 OF 连接：列出本项目已有连接；没有就“新建连接”新建表单：名称、API Key、Workspace Id；附“如何在 OF 创建 Key”手册链接
  3. AF 校验连接：调 HttpListOntologyModel成功 = 返回列表能读到；不能只看 HTTP 200 或 statusCode 0，要看 result 是否非空、字段是否完整
  4. 选择场景：列表展示名称、描述、对象类型 / 链接 / 行为 / 函数数量数据来自 API011 返回的 counts 字段
  5. 预览场景：调 HttpGetSemanticCatalog 展示对象、关系、指标同时生成子智能体用的目录摘要（见 08）
  6. 选择允许的能力：默认“只查询”；“执行行为”需单独勾选并二次确认
  7. 保存。调试面板里可以展开子智能体每一步调用了哪个接口、入参和返回

06 · 发布与广场

发布出去的智能体用谁的权限

发布时

  1. 发布检查：连接状态可用、绑定的场景仍存在（API009 读详情）
  2. 弹出确认：“发布后，所有使用者都会以连接 供应链本体·生产 的权限访问 OF 数据，看到的数据范围相同。”
  3. 发布快照里存 connectionId + ontologyModelId，不复制 Key

广场调用时

  1. 使用者不需要任何 OF 账号或 Key，直接用
  2. 调用记录标注“经由项目连接 xxx 访问 OF”，便于追查
  3. 连接失效时，智能体回答“本体服务暂不可用，请联系发布者”，并通知项目管理员
  • 数据权限不跟使用者走风险

    OF 文档里身份头 X-Ceai-User-Id 的语义不清楚。如果 OF 按 User Id 做行级权限，可以考虑把调用者身份透传过去；如果只认 Key，那广场上所有人看到的数据一样。一期按“只认 Key”设计，并把它写进发布确认。

  • Key 轮换不用重新发布建议

    因为发布快照只引用连接，项目管理员在连接里换 Key 后立即生效。换成另一个 Workspace Id 时要重新选场景，按“更换绑定”处理，需要重新发布。

07 · Claw 绑定

Claw 有两条路，先确认走哪条

冲突 2026-10-21 定过“Claw 能力库只放已发布资源；知识库、数据库、本体检索没有发布逻辑，要先在 AF 配给智能体并发布，再在 Claw 里召唤”。按这条，Claw 不直接绑 OF。你这次提到“在 Claw 绑定 OF”，两条路都写出来：

路径 A · 召唤已发布的本体智能体 符合现有决定

  1. 能力库 → 智能体 → 发现，找到绑了本体的已发布智能体（卡片上带“本体：订单履约”标记）
  2. 添加到我的 Claw
  3. 对话中 @ 它或由 Claw 自动召唤，走发布者的连接
不需要新概念。缺点：用户只能用别人发布过的场景，自己在 OF 有权限的场景用不上。

路径 B · 个人 OF 连接 建议放到 v2.0.1

  1. 能力库 → 插件 → 我的 → “连接本体”（和个人注册 MCP 放在同一处）
  2. 填 Key + Workspace Id → 校验 → 选一个场景，流程和管控端完全一样
  3. 生成一个个人的“本体助手”子智能体，只有本人可用
  4. Claw 主智能体通过它访问 OF；Claw 本身最多绑一个场景，换场景就是更换绑定
正好对上 v2.0.1 “个人资源：使用端直接注册、归个人所有、不走发布审核”的方向。个人连接不能被任何发布带出。

建议 一期做 A（零新增概念，管控端做完就能用），B 和个人 MCP 一起放进 v2.0.1。如果业务上强烈需要 Claw 直接连 OF，B 的流程和管控端共用一套组件，额外成本主要是“个人资源”这个归属模型。

08 · 子智能体还是挂工具

倾向子智能体，同意；内部优先用 OF 的高层语义接口

A · 工具直接挂在主智能体

  • 主智能体上下文里多出几十个接口定义，挤占其他工具的选择
  • OF 接口的参数很重（API001、API004、API012 请求字段都在 360 行以上），容易填错
  • 没有场景知识，主智能体不知道有哪些对象、编码是什么
不推荐。

B · AF 子智能体 + 精选工具 推荐

  • 主智能体只看到一个入口：ask_ontology(问题)，描述里写场景名和一句话简介
  • 子智能体的系统提示里放场景语义目录摘要（绑定时由 API103 生成），相当于自动生成的“本体 skill”
  • 子智能体只装运行时接口，分组见下表
  • 返回结构化结果：结论、用到的数据、口径、datasetID，主智能体可以继续引用
质量和可追溯性都在 AF 手里；代价是多一层调用的延迟和 token。

C · 直接转给 OF 问答

  • 子智能体内部只调 API105 提问 + API106 轮询，OF 自己的问答负责理解和查询
  • 接入最快，两个接口就够
  • 答案质量、口径解释在 OF 手里；交互卡片（RESPOND）要转给用户，体验割裂
可作为 B 里的一个工具或一期兜底，不建议作为唯一形态。

09 · 异常与边界

需要设计的状态

情况何时发现界面表现
Key 无效 / 过期新建连接校验、运行时连接标“失效”；绑定页提示更换 Key；运行时见 06
Key 有效但列不出场景新建连接校验“这个 Key 在该 Workspace 下没有可用场景”，提示检查 Workspace Id 或 OF 应用是否绑了场景
Workspace Id 填错新建连接校验同上。文档说 Workspace Id 不对时“看不到数据”，可能不报错只返回空，所以不能把空列表当成功
场景在 OF 被删除发布检查、运行时绑定卡片显示快照名 + “场景已不存在”，阻止发布
能力包不含某类能力运行时子智能体如实告诉主智能体“当前 Key 无此权限”，不重试
行为执行运行时执行前确认卡片：行为名、对象、参数；执行后按主键读回确认结果，不以 statusCode 0 判成功
10 · 操作手册大纲

“如何在 OF 获取 Key”手册要写的内容

  1. 登录 OF，进入目标工作空间，记下 Workspace Id（截图标出位置）
  2. 应用注册：新建调用方应用，绑定要给智能体用的本体场景
  3. API Key 管理：为该应用创建 Key；能力包建议只勾“查询”，需要执行行为再加
  4. 复制 Key（只显示一次的话要提醒保存）
  5. 回到 AF：新建 OF 连接，粘贴 Key 和 Workspace Id，点“校验”
  6. 常见问题：列不出场景、提示无权限、Key 轮换后要做什么、发布后别人用的是谁的权限
截图和字段位置要按 OF 当前页面实拍，本稿没有 OF 的“应用注册”“API Key 管理”页面快照。
11 · 待确认

要找 OF 核实或需要你拍板的

  • Key 的范围：整个工作空间，还是一个应用绑定的一个场景？找 OF

    决定绑定页是“列出场景让选”还是“显示 Key 对应的场景”。

  • 三个身份头怎么填找 OF

    Workspace Id 能否由 Key 反查（能的话表单少一个字段，但这算 OF 改造）；User Id 填 Key 创建者、AF 调用者还是固定值；Tenant Id 和 x-regionid 是否 AF 平台级配置即可；OF 是否按 User Id 做数据权限。

  • 失败时的错误码找 OF

    Key 无效、无权限、Workspace 不匹配分别返回什么。文档只有成功示例，校验逻辑要靠这个区分。

  • 网络与地址找 OF

    接口路径是 /http_rest_api/internal/v1/...，端口 9080，标的是 internal；AF 生产环境能否访问、是否有对外网关地址。

  • 本体 MCP 服务的工具清单和鉴权找 OF

    如果已有，子智能体直接挂 MCP，第 08 节的接口表就是筛选清单。

  • Claw 走路径 A 还是 B你拍板

    B 会推翻 10-21 “Claw 不直接选本体”的决定，建议随 v2.0.1 个人资源一起做。

  • 谁能在项目里新建 OF 连接你拍板

    只限项目管理员，还是有智能体编辑权限的人都可以。Key 背后是数据权限，建议只限管理员。

  • “执行行为”一期做不做你拍板

    建议一期只读，行为执行等确认流程和读回校验设计好再放开。
