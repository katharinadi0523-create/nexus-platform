# 会话排队、暂停与引导 PRD

## 1. 背景与目标

用户点击【停止】后，当前响应停止，未执行的队列消息保留并暂停。用户可点击【继续】恢复当前任务，也可发送新消息开始新一轮处理；新消息完成后，原队列按顺序继续执行。当前任务正常运行时发送的新消息仍进入队列，不打断当前任务。

本 PRD 同时明确输入区主按钮在发送、暂停和启动/继续之间的切换规则，并保留现有的队列管理与引导能力。

### 1.1 目标

- 停止当前响应后保留会话上下文和未执行队列。
- 执行中发送新消息时加入当前会话队列，不结束或替换当前任务。
- 停止后发送新消息时立即处理新消息，保留原队列并在新消息完成后继续执行。
- 用户能识别当前输入区主按钮会执行发送、暂停还是启动/继续。
- 队列消息按顺序处理，支持查看、编辑、删除、置顶和转为当前任务引导。

### 1.2 非目标

- 停止后发送新消息不弹确认框，也不自动清空原队列。
- 不改变会话权限、Agent 能力或模型选择逻辑。
- 不承诺所有工具调用都能在任意时刻被强制中断；不可安全中断时在安全节点暂停。

## 2. 术语与状态

- **会话**：承载消息、当前任务和待处理队列的对话上下文。
- **当前任务**：Agent 正在处理的这一轮用户目标；暂停后仍是同一个任务。
- **队列消息**：在当前任务执行中或暂停期间发送、等待后续处理的消息。
- **引导**：将一条队列消息作为补充指示提交给可继续执行的当前任务。
- **暂停**：保留当前任务和进度，阻止其继续推进；不清空队列，也不结束会话。

当前任务状态：

`idle → running → pause_requested → paused → resuming → running → completed`

运行中可因异常进入 `failed`。`pause_requested` 和 `resuming` 是过渡状态，不得呈现为暂停完成或恢复完成。

队列消息状态：

`queued → processing → completed`

可编辑或删除的仅为 `queued` 消息。暂停当前任务不会改变队列消息内容或顺序。

## 3. 输入区主按钮

### 3.1 状态优先级

主按钮根据“输入框是否有待发送内容”和“当前任务状态”共同决定。输入内容优先：用户已写好内容时，点击主按钮发送该内容；只有输入框为空时，按钮才控制当前任务。

| 输入框 | 当前任务状态 | 按钮显示 | 点击行为 |
|---|---|---|---|
| 有文本或附件 | 空闲，无当前任务 | 发送 | 创建并启动新任务 |
| 有文本或附件 | 执行中 | 发送 | 将消息加入队尾；当前任务继续 |
| 有文本或附件 | 正在暂停 | 发送 | 将消息加入队尾；当前任务继续完成安全暂停 |
| 有文本或附件 | 已暂停且队列非空 | 发送 | 立即开始处理新消息；原队列保留在其后 |
| 有文本或附件 | 正在恢复 | 发送 | 将消息加入队尾；恢复流程继续 |
| 无待发送内容 | 执行中 | 暂停 | 请求当前任务在安全节点暂停 |
| 无待发送内容 | 正在暂停 | 暂停中… | 禁用重复点击，等待暂停完成 |
| 无待发送内容 | 已暂停 | 继续 | 恢复同一个任务及其已保存进度 |
| 无待发送内容 | 正在恢复 | 启动中… | 禁用重复点击，等待恢复完成 |
| 无待发送内容 | 空闲 / 已完成 / 失败 | 禁用或保持现有空态按钮 | 不创建空消息 |

“继续”属于启动/恢复动作。若产品视觉规范要求按钮文案为“启动”，需同时提供明确的辅助标签或无障碍名称，避免用户误以为会创建新任务。按钮图标应与动作一致：发送、暂停、播放/继续；图标不能作为唯一状态提示。

有草稿时主按钮显示“发送”，因此用户仍可在任务运行时排队发送；此时若要暂停当前任务，需要先发送或清空草稿，使输入框为空，再点击“暂停”。这是单按钮设计的交互约束，需在界面上保持一致。

### 3.2 发送后的反馈

- 空闲会话发送成功后，消息进入会话记录并启动新任务。
- 当前任务执行中或正在暂停/恢复时，消息进入队列并显示“已加入队列”反馈及更新后的队列数量。
- 当前任务已停止且队列非空时，新消息立即开始处理；原队列数量和顺序不变，并在新消息完成后继续执行。
- 发送请求结果未知时显示“正在确认”，先核对服务端状态，不自动重复启动任务或创建队列项。
- 发送失败时保留输入草稿，不显示成功入队状态。

## 4. 暂停与继续

### 4.1 暂停

1. 用户在输入框为空且任务执行中时点击“暂停”。
2. 客户端提交暂停请求，当前任务状态变为 `pause_requested`，按钮显示“暂停中…”。
3. Agent 停止启动新的执行步骤；允许正在进行且不可安全中断的工具调用完成。
4. 系统保存可恢复断点、当前步骤状态及必要上下文。保存成功后状态变为 `paused`，按钮显示“继续”。
5. 暂停期间，队列消息仍可查看、编辑、删除、置顶或继续添加；这些操作不自动恢复当前任务。

暂停成功前不得显示“已暂停”。若工具调用等待外部结果，界面应说明正在等待安全暂停，不得将其伪装成已暂停。

### 4.2 继续

1. 用户在输入框为空且任务状态为 `paused` 时点击“继续”。
2. 系统校验任务断点、执行权限和必要资源仍有效。
3. 从同一任务最近一次已保存断点恢复，不新建任务，不重放已完成步骤。
4. 恢复成功后状态变为 `running`；当前任务完成后，再按顺序处理队列首条消息。
5. 如果没有可恢复断点或权限/资源已失效，保持任务暂停并说明原因，提供可执行的后续操作。

## 5. 排队与调度

### 5.1 发送与执行顺序

1. 会话空闲且没有待执行任务时，发送消息立即启动任务。
2. 当前任务处于执行中、正在暂停或正在恢复时，发送的新消息追加到当前会话队尾，不打断当前任务。
3. 当前任务执行中收到的新消息仅等待，不改变当前任务的输入上下文；它作为独立队列项，在当前任务完成后依次启动。
4. 当前任务已停止且队列非空时，发送的新消息立即成为当前任务，队列保持原样等待；新消息完成后，再处理队列首条。该操作不弹出确认框、不清空队列，也不恢复已停止的响应。
5. 用户在输入框为空时点击“继续”，恢复可恢复的当前任务；当前任务完成后再处理队列消息。
6. 队列中每条消息启动为独立任务，按入队顺序执行；用户置顶的消息排到下一条待执行位置。
7. 用户停止当前响应不会丢弃或自动消费队列。删除暂停队列中的最后一条消息后，队列区和队列暂停状态隐藏；新消息按普通对话立即处理。
8. 当前任务失败时不自动开始下一条队列消息，避免错误状态下继续执行；队列保留并等待用户处理。该策略为方案建议，需由产品和执行服务确认。

### 5.2 队列管理

- 队列显示在输入框上方并与输入框相连；队列为空时隐藏队列区域。
- 用户可查看、编辑、删除未执行消息，并可将消息置顶；本期不支持任意上下拖动排序。
- Hover 或聚焦时展示完整消息；触屏设备支持点击展开。
- 点击“编辑”将原消息载入输入框。重新发送后更新原队列项，保留其队列位置；取消编辑时不修改队列项。
- 置顶仅对尚未执行的消息有效；当前正在处理的消息不可置顶或编辑。
- 删除操作需有明确反馈；删除成功后队列数量同步更新。

## 6. 引导当前任务

1. 用户点击某条队列消息的“引导”后，将该消息提交为当前任务的补充指示。
2. 服务端确认受理后，该消息从队列移出并显示在会话记录中，队列数量减一。
3. 当前任务正在生成内容或执行工具时，已开始的输出或工具操作先到达安全处理点，再处理引导；多条已受理引导按提交顺序处理。
4. 同一时刻建议只提交一条引导；其他消息仍保留在队列中。
5. 当前任务已暂停且存在有效断点时，点击“引导”表示用户明确要求继续当前任务并应用该指示：先恢复任务，再处理引导。若产品希望“引导”不自动恢复，需另设行为，本期按自动恢复建议执行。
6. 当前任务已完成、失败或不再接受引导时，说明原因，并提供“加入队列执行”或其他可用操作。
7. 引导明确提交失败时，不从队列删除该消息；显示失败状态并提供重试或改为排队执行。送达状态未知时先核实，不自动重发。

## 7. 异常、幂等与恢复

- 当前工具操作无法安全暂停时，等待其结束后保存断点；若断点保存失败，不得显示“已暂停”，并需明确当前任务是否仍在运行。
- 继续时若断点不可恢复，不得静默从头重跑；提示用户可选的恢复、基于现有会话继续或重新执行方式。重新执行前说明可能重复外部操作。
- 暂停或继续请求因网络超时导致结果未知时，客户端先查询当前任务状态，再决定是否重试。
- 同一发送请求因双击或网络重试只创建一个任务或队列项；去重使用请求标识，不使用消息文本。用户主动发送多条相同文本应分别处理。
- 用户刷新或重新连接后，恢复当前任务状态、断点引用、队列顺序及消息状态；不重复已经完成的步骤或队列消息。
- 等待工具结果或用户审批时，暂停不得绕过审批或撤销已发出的外部请求；恢复前重新校验权限。
- 附件是否支持排队和引导由附件类型决定；不支持时在发送前说明原因，不能显示为已成功入队或已引导。

## 8. 数据、接口与权限要求

### 8.1 数据归属

- 当前任务、队列和引导状态必须关联 `session_id`；队列项还应关联唯一 `message_id`、队列顺序、创建者、创建时间、提交请求标识及状态。
- 可恢复任务需保存任务标识、当前执行状态、最近可恢复断点及上下文版本。断点不应复制超出恢复需要的敏感数据。
- 权限仍以服务端当前授权为准；旧断点不得使已撤销的会话、文件或工具权限继续有效。
- 删除队列项后应使其不再被调度；历史消息是否保留在会话记录中需与现有消息删除语义一致。

### 8.2 服务接口能力（方案要求，具体 API 待技术评审）

- 队列消息创建、查询、编辑、删除、置顶及顺序返回。
- 当前任务暂停请求、暂停状态查询、断点持久化、继续请求和状态回读。
- 引导提交及服务端受理状态回执。
- 所有写操作支持幂等请求标识；客户端以服务端确认结果更新界面。
- 队列和任务状态需在刷新、断线重连及多端访问后保持一致；并发修改时服务端返回冲突状态，客户端提示刷新，不静默覆盖。

队列容量、保留期限、跨设备同步、断点存储位置、附件限制、删除后的恢复能力和后台执行能力尚未确认，不在客户端擅自承诺。

## 9. 验收标准

### 按钮与任务

- 有草稿时主按钮显示“发送”；执行中的点击将消息加入队列，当前任务不改变状态。
- 输入框为空且任务执行中时主按钮显示“暂停”；点击后进入“暂停中…”，保存断点成功后进入“已暂停”。
- 输入框为空且任务已暂停时主按钮显示“继续”；点击后恢复同一任务，不从头重跑已完成步骤。
- 输入框为空且正在暂停/恢复时，按钮显示对应进行中状态并阻止重复请求。
- 停止后队列非空时发送新消息，立即开始处理新消息；原队列不变，并在新消息完成后按原顺序继续执行，不弹确认框。

### 队列与引导

- 运行中连续发送多条消息均按服务端确认顺序入队；当前任务完成后按队列顺序执行。
- 暂停、刷新、重连后任务断点和队列消息仍存在且顺序不变；继续后先完成当前任务，再执行队列。
- 删除、编辑、置顶只影响对应的未执行队列项；队列为空时隐藏队列区，但不能因此清除暂停任务。
- 引导受理后队列项转入会话记录并从队列移除；提交失败或状态未知时不丢消息、不重复执行。
- 当前任务失败时队列不自动启动，且有明确状态和后续操作提示。
